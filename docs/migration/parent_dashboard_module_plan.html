01 Context & Scope

It uses the shared theme2/dashboard/Dashboard.jsp shell with a DB-driven menu (USER_RIGHTS, MODULES). 02 Approach — no toggle

Unlike the Student dashboard there is no PARENT_DASHBOARD_VIA_NEXTJS toggle. Every PARENT entry point redirects straight to the Next.js dashboard, so cutover happens when the backend and frontend are deployed. Rollback is a code revert, not a settings row. The release therefore needs a full pass in UAT before prod (Phase E).

Only safety net: blank NEXTJS_APP_URL If NEXTJS_APP_URL is blank in an environment, the parent redirect falls back to the legacy JSP. This is a config guard, not a toggle.
Branches (decided) Next.js work goes on a new branch that you create and move to. Backend work stays on feature/63_0_0_STUDENT_DASHBOARD_NEXTJS_PHASE4. No commits or pushes are made by Claude; changes stay in the working tree.
Reuse as-is (do NOT rebuild) Auth and SSO (app/api/sso, lib/auth/*), proxy.js account picking and refresh, DashboardShell, Sidebar, DashboardTopHeader, RightActionRail (announcements, diary, chat), PermissionGate/useModuleRights, mapBackendMenu, services/dashboardApi.js, utils/backendRequest.js, session-expiry hooks and dialog, ChangePasswordModal, components/ui/**, components/common/**, and the student feature components (Attendance, LoginHistory, FeeDetails, Performance, ProgressReports, Syllabus) once made child-aware.

06 Phase B — Child Selection Layer core of the parent work

  • Service: getStudentsByParent() in services/dashboardApi.js returns studentBasicDetails[] (studentId, studentName, userId, standardName, studentStandardId, courseProvicerId, learningProgramName, studentTimezone, profilePic).
  • Provider: ParentChildProvider and useSelectedChild expose {children, selectedChild, selectChild, isLoading}. The selected id is always validated against the children list. An unknown id opens the picker.
  • Where it lives (changed, Phase C review): not in the URL, so no child id sits in the address bar to read or edit. It is held in ParentChildProvider (the page's memory) and mirrored to sessionStorage per account (this tab only), which is how it survives a reload. The stored id is trusted only after it is found in the gate's children list; anything else opens the picker. With several children nothing is selected until one is picked (the picker shows); a parent with one child has it selected. Deep links to a specific child are given up on purpose. An old ?child= in a bookmark is stripped from the address bar. This is a convenience, not the access check: every parent endpoint verifies server-side that the child belongs to the signed-in parent, so an edited request is refused whatever the browser sends.
  • UI (changed again after the legacy screenshots of 2026-11-13: cards, not tabs): the first screen is the child picker (ChildPicker): "Hi {parent first name}, which dashboard would you like to open?", "You have N children linked to this account. Pick one to continue.", and one card per child (photo or initial, name, grade with a cap icon, "View Dashboard"; the whole card is the button; 4 per row on very wide screens, 3, 2, 1; on phones a compact card). While the picker shows, the page has no sidebar, no hamburger and no right rail. "Add Another Child" (when the school has it on) sits under the cards. Choosing a card opens that child's dashboard; SelectAnotherChildButton (right-aligned above every parent page, only with 2+ children) clears the choice and brings the picker back. A parent with one child skips the picker. This replaces the tab strip of the previous step. Header dropdown (added 2026-11-13): ChildSwitcher in the parent header lists all the children (name and grade, the current one ticked); choosing one switches the whole dashboard to that child straight away, from any page, without going back to the picker. Shown only with 2+ children and once a child is chosen; on phones only the avatar and arrow show; keyboard: Escape closes, Up/Down move. Modules follow the choice and none has a picker of its own.
  • Status (built in Phase B): hooks/parent/useSelectedChild.js (ParentChildProvider mounted around the shell for parents only, plus useSelectedChild; no withChild, nothing to carry in links), ChildPicker (the cards screen) and SelectAnotherChildButton (above every parent page, in parent/layout.jsx), ChildAvatar, ParentChildRequired (every parent page wraps in it). Because parent pages have their own hooks (Q20), the student hooks and services do not get a child parameter, so the next two bullets are superseded: parent hooks take the selected child's id and put it in their query key.
  • Superseded by Q20 — make the data layer child-aware, non-breaking: every dashboardApi function that hardwires studentUserId: userId (L339, 358, 376, 520, 536, 551, 587, 602, 618, 642, 659/676) gets an optional studentUserId that defaults to userId. services/attendanceApi.js L21-27 is the template. Hooks accept studentUserId and add it to the query key, so switching child refetches.
  • One adapter: hooks/useDashboardSubject.js returns context.userId for a student and selectedChild.userId for a parent. Shared components call it instead of reading context.userId.
  • Session-derived services (profile, withdrawal, anything using buildBody(me)) need an explicit studentUserId only where the endpoint is child-scoped.
WatchuseDummyStudent is wired into almost every hook and is keyed on context.userId. Parent demo mode is skipped in v1, so on the parent path the hooks must treat dummy mode as off.

07b Phase C2 — Theme follows the selected child added after Phase C NOT being done (user decision 2026-11-12)

Decision (2026-11-12): this theme phase is not being done Phases D1, D2, D3 and E are built first, with the default theme, and this phase (C2) follows once they are done. The label "C2" is kept because the section was added after Phase C; in time it comes after E. Until then every child gets the default theme, and nothing in the work above waits on this. The theme sub-decisions below (Q21a, Q22 to Q24) stay open until then.
Requirement (settled) A parent with three children, one in elementary, one in middle school and one in high school: when the parent selects the elementary child the whole dashboard (shell, header, menu rail, pages) is in the elementary (K-5) theme; the middle child gives the middle theme; the high-school child gives the high-school theme. The theme itself is already built for the student dashboard and is reused, not redrawn.

How the student theme works today (what we reuse)

  • Band: the backend decides gradeBand (ELEMENTARY / MIDDLE / HIGH) in GradeBandUtil.resolve(standardId): name overrides first ("elementary", "middle", "high school", "advanced placement", ...), then STANDARD.ORDER_ID against two CONFIGURATION settings, default MIDDLE. utils/gradeBand.js only holds a fallback table.
  • Theme choice (useResolveGradeBand): isK5 = (ELEMENTARY, or MIDDLE when NEXT_PUBLIC_MIDDLE_DASHBOARD=true) && K5_DASHBOARD_ENABLED && a K5 learning program. isMiddle picks the Balanced skin (app/k5-middle.css), isPreK (standard 17) the simpler variant.
  • Shell: isK5 gives K5Shell (AppearanceProvider scope="k5", .theme-k5 tokens, K5Header, K5NavRail, Pico guide, rail variant="k5"); otherwise DashboardShell. Feature pages render their components/k5/pages/K5* variant when isK5.
  • The parent today always gets DashboardShell: the grade gate is student-only, so the parent has no band.

What the parent needs

  1. Per-child theme data from the backend (Phase C2, small). get-students-by-parent already returns each child's studentStandardId but not the band. Add per child, in the existing loop, using the same helpers the student gate uses: gradeBand (gradeBandUtil.resolve(standardId)), standardId, registrationType and isSelfStudy; and once at the top level k5DashboardEnabled (school-wide K5_DASHBOARD_ENABLED). Few extra queries per child. The parent gate alone then themes every child, with no extra call.
    Not used on purpose: calling the student's get-student-dashboard with the child's id works today, but that endpoint takes the user id from the body with no ownership check (a gap to fix, not to build on).
  2. useChildTheme() (new, hooks/parent/). From the selected child plus the gate's k5DashboardEnabled it returns the same {gradeBand, isK5, isMiddle, isPreK, isSelfStudy} the student gate does, with the same rules and the same fallback (unknown band is MIDDLE, as the backend does).
  3. Shell choice for a parent. ShellForGrade reads the child's theme instead of the student grade fields when the role is parent. A parent with children always has a selected child (Child 1 by default), so the theme is known from the first paint; a parent with no children, and any state where the theme is unknown, use the neutral DashboardShell. The selected child lives in ParentChildProvider, which wraps the shell, so switching child swaps the shell without losing state or reloading.
  4. Make the K-5 chrome role-aware (as Phase A did for Sidebar and the header): K5NavRail, K5Shell and K5CompleteProfileModal use studentNavHref; K5Shell renders its own RightActionRail, which needs the same parent props as DashboardShell gives it (studentUserId = selected child, no News, hidden on phones); the K-5 header needs the parent variant of the cart / profile / Add Another Child items.
  5. Parent pages inside the K-5 theme. Parent pages are their own components (Q20) written for the default tokens, so under .theme-k5 they must still look right. Recommended first step: wrap parent content in the k5-legacy compatibility scope the shared rail panels already use (app/k5-modules.css), so default-themed components take the K-5 / Balanced tokens. Dedicated K-5 variants of individual parent pages (components/parent/k5/*, as the student has components/k5/pages/*) are a later, per-module choice. Phase B and C components (child picker, home) are reviewed in all three themes in this phase.

Rules and edge cases

  • The three bands for one parent: Elementary gives K-5; Middle gives the Balanced skin only when NEXT_PUBLIC_MIDDLE_DASHBOARD=true (otherwise default, as for students); High gives the default theme.
  • K5_DASHBOARD_ENABLED off, or a learning program that is not a K-5 program: default theme for that child, as for a student.
  • Switching child changes the theme at once; reload keeps the child (not in the URL), so it keeps the theme.
  • The appearance choices inside the K-5 theme (USER_THEME, saved with update-theme by user id) belong to the parent's own account, one setting across all the children; the backend update-theme call takes the user id from the body with no session check, so the parent app must only ever send the session user's id.
  • The Pico guide and its page tips are written for a student: hidden on the parent dashboard.
  • The theme never changes what data or menu the parent gets: menu and rights are the parent's role, data is the selected child's.

Open sub-decisions (recommended answers in section 13)

Q21 where the per-child theme data comes from, Q22 how parent pages look in the K-5 theme, Q23 who owns the appearance choices, Q24 Pico guide for parents, Q25 which theme shows before a child is picked (no such state now: Child 1 is selected from the start).

EffortBackend: a few lines in getStudentsByParent (check that GradeBandUtil and the standard service are injected there). Frontend: one hook, a few role-aware changes in K-5 chrome files, and a visual pass of the parent pages in each theme. The theme code itself is not rewritten.
