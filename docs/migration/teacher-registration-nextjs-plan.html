Teacher Registration on Next.js

The plan for moving the legacy teacher sign-up wizard (SignupCommonTeacher.jsp + theme2/teacher/SignupTeacher.jsp) out of the Java app and into is-sms. It uses the same approach as the student enrollment migration: the existing backend APIs stay in place, emails and logins hand off to Next.js through single sign-on, and a per-school setting can switch the new flow on or off.

01

Summary

Most of the teacher flow already exists on the backend. What's missing is the bridge into Next.js and a new UI.

  • The backend business logic is done. ClientSignupTeacherController and SignupTeacherUtil already save every stage, run the demo recording on Lens, generate the contract PDF, handle verification and bank details, and send all the emails. About 20 of the stage endpoints already accept and return JSON (an encoded payload), the same way the student endpoints do.
  • The bridge is missing. Students who log in or click through from an email are sent to Next.js with a one-time SSO token (/api/sso?token=…). Teachers are still sent to the JSP page /teacher/signup/process/{uuid}, and nothing in the teacher code creates an SSO token.
  • The UI must be rebuilt. That means 6 wizard stages, an account-creation page, and about 15 modals and lock screens, including the live demo recorder (start a Lens meeting, poll for recordings, re-attempt, pick a recording, play it back).
  • A few new backend APIs are needed:
    • a teacher "registration process" endpoint (the student one returns 403 for teachers);
    • a stage-status endpoint, so the page can notice when an admin approves the teacher;
    • a GET for saved bank details (none exists, so the form is always blank);
    • a file-upload path that handles documents up to 10 MB;
    • a role field on the SSO exchange response;
    • a "continue registration" email link that creates a fresh SSO token when clicked.
About "signupTeacher.jsp"

No file with that exact name exists. The legacy page is is-rest-api/src/main/webapp/WEB-INF/views/theme2/teacher/SignupTeacher.jsp, with account creation in theme2/SignupCommonTeacher.jsp. This plan assumes those are the pages being replaced. The data they collect already reaches the backend through the JSON endpoints listed in section 06.

No teacher webhook will be built. The external careers site (new-website) already sends teacher applications to save-teacher-screening-data, which belongs to the screening pipeline. The Next.js sign-up page calls the existing stage-1 API directly.

The numbers 11–15 mean different things for students and schools. Every new check must test the role and firstReset, never firstReset alone.

Two teacher pipelines feed this wizard

  • A. Self sign-up. The account form, then stage-1, then the wizard from Step 1. This is the main scope of this plan.
  • B. Job application / screening. USER_SCREENING: an applicant uses public AES-link pages with no login (tracker, questions, book-a-meeting, accept terms). When an admin sets "Approved for Selection Process", a User and Teacher are created at firstReset 11, and an invite-password email drops the teacher into the same wizard at Step 2. Pipeline B's public pages are out of scope until P8, but its invite email must land in Next.js.
03

Target flow and single sign-on

This follows the student pattern exactly, with one change: emails never contain the 5-minute token itself.

1
Account creation in Next.js/{school}/teacher-registration posts to the existing api/v1/teacher/enrollment/stage-1. When the setting is off, the page redirects to the JSP /{school}/teacher/signup, the same way isEnrollmentViaNextjs works for students.
2
Backend returns an SSO URL instead of a JSP URLWhen the setting is on, the stage-1 redirectUrl (SignupTeacherUtil:335), the login redirect (CommonUtil.getLogin:2039) and the dashboard redirect (SingleSignOnUtil.getDashboardRedirectUrl:251) all call a new getFinalTeacherRegistrationUrl(). It creates a token with the existing createSsoToken() and builds <NEXTJS>/api/sso?token=…&flow=teacher&step=N&school=…&backend=….
3
Email links go through a "continue" endpointTeacher emails (verify, approved, verification requested, contract accepted, invite-password) link to a new {school}/teacher/registration/continue?payload=…. The payload is an encrypted user id plus an expiry time. A link stays valid for 72 hours and works more than once in that window. Each click is checked by the backend, which creates a fresh 5-minute SSO token and redirects to /api/sso. An expired link falls back to the login page, which still lands in Next.js through step 2.
4
/api/sso handles teachersapp/api/sso/route.js reads flow=teacher (an explicit flag, like ae=Y), checks the step against a teacher list of valid steps, signs in with the existing "sso-token" provider, then sends a 303 redirect to teacherStepPath(school, step).
5
The wizard resumes from the backendA new GET api/v1/teacher/registration/process/{uuid} returns firstReset, the mapped page and lock state. A cloned resume hook sends the teacher to the right step or lock screen. Locked screens poll a teacher stage-status endpoint, so an admin approval moves the teacher on without them logging out and back in.
6
CompletionAfter bank details (firstReset 0), the teacher is sent to the legacy /{school}/dashboard/teacher/{uuid} using the existing hash-POST helper (withLoginPayload). The teacher dashboard is not migrated yet.
Correction from the first draft

The first draft said SsoExchangeResponse had no role. On the current backend branch it already returns userRole (the parent role, e.g. TEACHER) and roleId, added for the student dashboard. The exchange works for teachers as it is. P1 only adds firstReset, so the Next.js session knows the registration stage. The stage numbers overlap with student and school stages, so it is always read together with userRole.

04

Phase overview

The work has 8 delivery phases (P0–P7) plus one optional later phase (P8). P1 (backend) and P2 (frontend shell) can run in parallel once P0 is settled. From P3 onward, each phase delivers working stages end to end.

Review gate after every phase

Each phase ends with a stop. The diff from both repos is presented together with what was tested in the browser. Nothing is committed until it has been reviewed and approved, and nothing is pushed without separate approval. The next phase starts only after that.

Phases in detail

P0

Groundwork

both repos

All design decisions are settled (see section 11). P0 sets up the branches and a local environment where every later phase can be tested end to end.

Branches & setting

  • Backend: feature/63_0_0_TEACHER_REGISTRATION_NEXTJS_PHASE1. It has no teacher commits yet, and its tip already contains the student SSO code.
  • Frontend: feature/version_1_4_0_teacher_registration (identical to main today).
  • New global setting key: CONFIGURATION / TEACHER_REGISTRATION_VIA_NEXTJS, separate from ENROLLMENT_VIA_NEXTJS. The SETTINGS table has no school column, so the setting can only be on or off for every school.

Local test environment

  • is-rest-api: dev profile via mvnw (Java 25, port 8080, context /), using the database from the VS Code launch config. No Redis.
  • Uploads go to the testseri bucket automatically: under the dev profile, SCHOOL_SETTINGS_AWS resolves to its TESTING row.
  • is-sms: the existing .env.local already proxies to localhost:8080.
  • Test teachers use dummy addresses (e.g. teacher.test1@example.com). Email links are read from the backend logs.
  • Admin approval clicks in the legacy admin dashboard and one real demo recording are done by hand during testing, following a checklist.
ExitBoth apps run locally; a test teacher can sign up on the legacy JSP flow locally; branches are checked out.
P1

Backend bridge

is-rest-apimostly new code

Teach the backend to send teachers to Next.js and add the few APIs the new UI needs. No stage business logic changes.

SSO & redirects

  • SQL external-resource/64_x_x_TEACHER_REGISTRATION_NEXTJS.sql (ddl-auto is none): insert the TEACHER_REGISTRATION_VIA_NEXTJS setting, defaulting to false. The SSO_TOKENS table is reused unchanged.
  • CommonUtil.isTeacherRegistrationInProgress(user): role is TEACHER, and firstReset is neither 0, 1, 15 nor 25.
  • CommonUtil.getFinalTeacherRegistrationUrl(user, office): copy getFinalEnrollmentUrl, adding flow=teacher and step taken from the firstReset map. Optionally shorten it with TinyURL like the student URL.
  • Add the teacher branch, gated by the setting, at:
    • CommonUtil.getLogin:2039
    • CommonUtil.getRedirectUrl:2341
    • SingleSignOnUtil.getDashboardRedirectUrl:251
    • the stage-1 redirectUrl at SignupTeacherUtil:335
  • When the setting is on, the JSP entry pages {school}/teacher/signup (controller :63) and /teacher/signup/process/{uuid} (:141) redirect to Next.js, the same way commonSignupContent:290 does for students.
  • Add firstReset to SsoExchangeResponse and fill it in exchangeSsoToken. The role is already there as userRole. This is additive, so the student flow is unaffected.
  • reCAPTCHA: SignupUtil.validateSignup:897 skips the check for teacher stage-1 whenever ENROLLMENT_VIA_NEXTJS is on. Make the teacher skip depend on TEACHER_REGISTRATION_VIA_NEXTJS instead. The JSP flow keeps its check, and Next.js verifies reCAPTCHA on its own server.

New JSON APIs

  • GET {school}/api/v1/teacher/registration/process/{uuid}?hash=: returns firstReset, signupPage, the wizard step (1–6), and a state: FORM, LOCKED (lock reason UNDER_REVIEW or VERIFICATION) or REDIRECT for declined, withdrawn or completed teachers. The "contract expired" case is not a state here: it comes from the existing agreement-details response and is handled inside the Contract step (P5). It reuses the logic of signupTeacherProccess, with one fix: firstReset 20 (a legacy state no admin option can set any more) opens the Contract step, the same as 14, instead of falling through to Step 2.
  • Teacher stage-status endpoint for lock-screen polling, shaped like the student SignupStageStatusResponse (status, signupPage, redirectUri).
  • teacher/signup/get-teacher-bank-details, so Step 6 can be prefilled. Mask the account number in the response.
  • teacher/signup/upload-document, a multipart endpoint that takes one file plus its fileType. Storage is the same as legacy teacher uploads: AttachmentUtils logic, the bucket from SCHOOL_SETTINGS_AWS (testseri locally), public-read, and the ATTACHMENTS row upserted per (LOGIN_ID, ATTACHMENT_TYPE). Two things differ:
    • The S3 upload is synchronous, so the response reports a real success or failure.
    • Files are checked on the server: 10 MB at most, JPG/PNG/PDF only.
    The Step 2 and Step 5 save methods do not change: they already keep any attachment that is not re-sent.
  • Every new endpoint (process, stage-status, bank GET, upload, continue) checks userLoginHash against the user. The existing shared endpoints stay as they are, the same as for students. Adding the check there would break the legacy JSP flow, which sends a random hash.
  • Any timezone code that is new or touched must fall back to Asia/Singapore when the timezone is missing or invalid, and must never overwrite a valid configured one (project rule).
ExitWith the setting on in UAT, a teacher at firstReset 11 logs into the JSP login and is redirected to <nextjs>/api/sso?…&flow=teacher&step=1 (step 1 is Personal Details; firstReset 12 gives step 2, and so on); exchanging that token returns userRole=TEACHER and the firstReset. With the setting off, nothing changes for anyone.

is-smsclone student infra

Get a teacher from the backend redirect into a signed-in wizard shell with all six steps as placeholders. This copies the final student structure, not the student first draft.

Auth & routing

  • app/api/sso/route.js: add a flow=teacher branch with its own list of valid steps (1–6), using teacherStepPath(). Keep the 303 redirect, the backend override cookie and the safe-path checks.
  • proxy.js: add /:school/teacher-registration/step/:path* to the protected routes and /:school/teacher-registration to the public-landing backend-cookie branch.
  • next.config.mjs: add the no-store header and the dev rewrites for the teacher paths.
  • utils/authentication.js: make userType a parameter (it is hard-coded to "STUDENT" today).

Shell & state

  • utils/teacherRegistrationSteps.js: the single source for the six step slugs and teacherStepPath().
  • step/layout.jsx and TeacherWizardChrome.jsx mount the provider and the shell once, not once per step.
  • hooks/useTeacherRegistrationContext.js: reads the session, the process endpoint and the setting gate, which redirects to the JSP via a new legacyTeacherRegistrationUrl(). It calls recordApiAttempt() so error reports carry useful diagnostics.
  • hooks/useTeacherWizardResume.js: copies the window.__wizardResumeChecked latch and the synchronous redirecting flag.
  • services/teacherSignupApi.js (public) and services/teacherSignupBackendApi.js ("use server", payload envelope, no cookie forwarding).

  • PageTitle.jsx: give teacher routes their own tab title, and never call student endpoints there.
  • EnrollmentPixel.jsx: add teacher-registration to the route regex, so the Meta pixel also runs on teacher pages.

P3

Account creation + Step 1 Personal Details

is-smsexisting APIs

A brand-new teacher can create an account and save personal details. firstReset reaches 11.

Account page /{school}/teacher-registration

  • Fields: Email (max 50), Confirm Email, Password and Confirm, and a Terms checkbox linked to the school's Terms and Privacy URLs. The button reads "Sign Up".
  • Password rules (shown as a tooltip and checked live): 8–20 characters, at least one each of uppercase, lowercase, digit and a special character from !@#$%&*; no sequences, keyboard patterns or repeated characters.
  • On email blur, call is-user-available:
    • invalid email → EmailValidatorModal;
    • status 0043/0044 → Already registered;
    • status 02 → Not approved.
  • Submit to api/v1/teacher/enrollment/stage-1 with userType:'TEACHER', the password encoded with encodeRawString, UTM cookies and location. Use invisible reCAPTCHA v3 with action teacher_signup, verified server-side by cloning the student helper.
  • On success, follow redirectUrl straight into the wizard, the same as students. The backend still sends the verification email in the background, and there is no blocking "check your email" screen. A blocking screen would be cosmetic anyway, because unverified users can already log in.

Step 1 Personal Details

  • Load from teacher/signup/get-teacher-basic-details.
  • Fields:
    • First, Middle (optional) and Last name: letters only, max 40, title-cased.
    • Country, State and City as cascading selects. Country is locked when SCHOOL_ID is 5.
    • Date of birth: age 18–99, sent as mm-dd-yyyy.
    • Gender: MALE, FEMALE or DONOTWANTTOSPECIFY.
    • Email: read-only.
    • Phone: reuse useIntlTelInput and PhoneNumberField, and send the dial code and number as separate fields.
  • Save to teacher/signup/save-basic-details and await the response before moving on. If the save fails, show the error and stay on the step.
  • Fix the legacy firstReset 9 empty page: show Step 1 empty and ready to fill.
ExitSign up, land in Step 1 through SSO, save Step 1, refresh: the data persists and the teacher is on Step 2. Duplicate and declined emails show the right modal.
P4

Step 2 Professional Details + live demo recorder

both reposlargest phase

This is the hardest step. It has five document uploads, grade and course pickers, a declaration, and the Lens demo recording loop.

Form, pickers, documents

  • Load from get-teacher-academic-professional-details and get-teacher-signup-subject-details.
  • Fields:
    • Highest degree, from a fixed list of 6.
    • Specialization (max 100).
    • Experience: 1–20 years.
    • Last organization (max 100).
    • "Why should we hire you?" (max 200).
  • Grades Taught dialog: multi-select. Schools 1 and 6 offer KG–12; others offer 1–12.
  • Courses Taught dialog: Elementary, Middle and High tabs, multi-select, with selected chips. At least one course is required.
  • Uploads (JPG, PNG or PDF, max about 10 MB):
    • Highest Degree (fileType 2)
    • CV (4)
    • Work-Experience (3, optional)
    • Passport/National ID (19)
    • Internet Speed Test screenshot (75)
  • Uploads: each file is uploaded as soon as it is picked, straight from the browser to the P1 upload-document endpoint. It never goes through Next.js, because Vercel limits request bodies to about 4.5 MB. Every file gets its own progress bar and error message. Picking a file again replaces the stored one. The stage save sends no attachments; the backend keeps what was uploaded.
  • Declaration checkbox declConfirmation, with the school name inserted into the text.
  • Save to save-academic-professional-details and await the response. Legacy moves on before the save completes, which is a bug.

Demo recorder drawer

  • Read the maximum number of attempts from the TEACHER_DEMO_RECORDING_ATTEMPTS setting (default 2).
  • "Live record your demo" validates and saves the form first, then calls create-teacher-registration-demo-meeting with title, start time, 30-minute duration, timezone, meetingType 1 and gmType 16.
  • Timezone comes from the user's timezone. If it is missing or can't be resolved, fall back to Asia/Singapore.
  • start-teacher-registration-demo-meeting?payload= returns a host URL. Open it in a new tab and show the Start Demo / Copy Link dialog.
  • Poll get-teacher-demo-recordings every 10 s with React Query's refetchInterval, for up to 40 minutes. Stop once every session has a recording.
  • Each attempt row shows one state:
    • in progress;
    • invalid (start equals end);
    • under 1 minute;
    • recording processing;
    • ready, with Recordings and a select option.
  • Re-attempt calls teacher-demo-recording-reattempt-by-teacher, then starts a new meeting.
  • Playback uses videos/signed-url and plays in a <video> modal. Archived recordings (Glacier or Deep Archive) can't be played. The transcript comes from transcript/show-content.
  • The chosen recording is saved as demoMeetingId with the stage. Teachers with a saved demoVedioLink keep the old "paste a demo link" mode.
  • Watch out: get-teacher-demo-recordings and create-…-demo-meeting expect a raw JSON body, not the payload envelope.
ExitThe teacher records a demo, sees it become playable, picks it, saves, and firstReset becomes 12. Refreshing mid-recording resumes polling. Re-attempts stop at the configured limit. Meeting creation and the polling and table logic are tested automatically in the browser; one real recording run is done by hand, following a checklist.
P5

Step 3 Review, review lock, Step 4 Contract

is-sms

The teacher submits for review, waits for an admin decision, then signs the contract.

Review & lock

  • Step 3 is read-only, with Personal and Professional sections. Edit returns to Step 1 or 2 and reloads their data (legacy only switches tabs). The demo "View" opens the recording.
  • Next opens the Note confirmation ("no changes once submitted"). Submit calls profile-confirmation (SEND_MAIL_FOR_PENDING_APPROVAL) and firstReset becomes 13.
  • Demo Under Review lock screen, for firstReset 13 and 24: its only actions are Log out and Check status. It polls the stage-status endpoint every 30 seconds, so approval (14) moves the teacher to Step 4 automatically.

Contract

  • Load from get-teacher-signup-agreement-details. If validityEnd is missing or in the past, show the Contract Expired lock (Log out only) and stop.
  • Render the agreement HTML sanitized with DOMPurify, since the HTML comes from the backend. Show the logo, or the letterhead for WLP schools, plus the recipient block and date.
  • Signature upload: JPG or PNG, 300 KB or less. It is placed in the signature box and today's date is filled in. Add the "Acceptance of Offer" checkbox.
  • "Accept Contract" opens the Are you sure? dialog. Yes calls save-Teacher-Declaration with the contract HTML (including the signature), plus ip-api location JSON and browser details. firstReset becomes 22. The backend uses decodePreservePlus.
  • Back is hidden on Steps 4–6, as in legacy.
ExitSubmit, then an admin approves in the legacy admin dashboard; the teacher's lock screen moves on to the contract by itself. Signing produces the PDF email and firstReset 22.
P6

Step 5 Verification, Step 6 Bank, completion

both repos

Background check documents, the second review lock, and bank details. This is where registration completes.

Verification

  • Load from get-teacher-verification-details.
  • Social media: LinkedIn, Facebook, Instagram and X. At least one is required, or the teacher ticks "I do not have any active social media accounts", which clears and disables the four fields.
  • Recommendation letters 1 and 2 (fileTypes 73 and 74).
  • References 1 and 2: name, email, phone (intl-tel) and designation are all required.
  • Police verification declaration (shows the teacher's name), Police Verification document (72) and Last Salary Slip (41).
  • Show validation messages in the legacy order. The Note confirmation then calls save-teacher-verification (it has no authentication block) and firstReset becomes 21.
  • Documents Under Verification lock screen, which polls like the P5 lock. When an admin redirects the teacher to bank details (23), they go to Step 6.

Bank & finish

  • Prefill from the new get-teacher-bank-details (legacy is always blank).
  • Fields:
    • Currency, account number, IBAN, and account type (Savings, Checking or Current). Fix the legacy placeholder value " ", which lets an unselected type through.
    • Holder first, middle and last name; address; country, state and city; postal code; phone; email.
    • Bank name, branch name and branch address; country, state and city; postal code.
    • Optional: SWIFT, IFSC, routing number and other details.
  • Submit to save-teacher-bank-details (accountType:'BANK_ACCOUNT'), and firstReset becomes 0.
  • Show "Redirecting to dashboard", then hash-POST to the legacy /{school}/dashboard/teacher/{uuid} using withLoginPayload.
  • The process endpoint returns REDIRECT for firstReset 0, so a stale tab can't reopen the wizard.
ExitA teacher goes from sign-up to the teacher dashboard without opening a single JSP wizard page.
P7

Email deep links, hardening, QA, rollout

both repos

Every teacher email leads into Next.js, the flow survives real-world use, and the release goes out safely.

Emails (single sign-on)

  • Add the "continue" endpoint {school}/teacher/registration/continue?payload=. The payload is an encrypted userId|expiry. A link is valid for 72 hours and works more than once in that window, so a second click or an email scanner opening it first doesn't break it. Each click creates a fresh SSO token, then redirects to Next.js. Expired links go to the login page.
  • Point the #URL# in these templates at it when the setting is on:
    • TEACHER_PROFILE_APPROVED_REDIRECT_TO_BANK
    • TEACHER_PROFILE_APPROVED_REDIRECT_TO_VERIFICATION
    • TEACHER_CONTRACT_ACCEPT_MAIL
  • After email verification (/common/verify-email) and the invite-password flow (/common/invite-password), redirect teachers through SSO instead of to the JSP login.
  • Under-review, decline and on-hold emails have no link. They need no change.

Hardening, QA, rollout

  • Reuse useBackendSessionGuard, the window.__loggingOut guard, the pageshow reload for pages restored from the back/forward cache, and error forwarding to sms-error-log.
  • QA matrix:
    • every firstReset value × {fresh login, email link, refresh, second tab};
    • mobile layouts, including the demo drawer and contract on phones;
    • UAT backend switcher;
    • setting on and setting off.
  • Regression check on the student SSO, login and enrollment flows. Shared files change in P2.
  • Rollout (the setting is global, so there's no per-school stage):
    1. full test pass on UAT with the setting on;
    2. deploy to production with the setting off;
    3. switch the setting on;
    4. monitor the error logs for a week.
    Rollback is turning the setting off; the JSP flow is untouched.
ExitThe setting is on in production; a week of error logs shows no teacher-flow regressions; the legacy JSP stays available as a fallback.

Security: what is checked and what isn't

No existing stage endpoint, student or teacher, validates userLoginHash today. They trust the userId inside the payload, and their session checks are commented out (e.g. SignupTeacherUtil:374, :1925, :2510). The legacy JSP sends a random number as the hash, so enforcing a check on these shared endpoints would break the legacy flow, which is also the rollback path.

Decision: every new endpoint checks userLoginHash. These are process, stage-status, bank-details GET (which returns bank data), upload-document and continue. The gap in the existing endpoints is recorded as a separate task covering both students and teachers.

Lessons from the student migration

Each of these cost the student flow a fix commit. The teacher flow should get them right from day one.

Do thisBecause
Use named step routes /{school}/teacher-registration/step/{slug} from the startThe flat /step/N routes had to be rebuilt on day 4 (6 commits).
Mount the provider and shell once, in step/layout.jsxMounting per step repeated the logo, school info and location side effects.
Save on every step and await the result; no batched client savesBatched saving was reverted after refreshes lost data (8dda26e).
Check status === "1", never statusCodeFailed saves were being reported as success (756e268).
Send the phone dial code and number separatelyThe backend decode turns + into a space.
Route SSO by an explicit flag (flow=teacher)Inferring the flow from next broke routing (e6863e6).
Declare every signIn() credential in the provider schemanext-auth silently drops undeclared fields (7c136f4).
Pass only serializable values to Server ActionsPassing URLSearchParams broke (42806e4).
Never call record-creating endpoints from passive componentsPageTitle created a new child record on every refresh.
Treat stale tabs and copied URLs as normalAlready-paid results and URLs opened without a session needed fixes (ad7d485, 90c2f30).

Risks

RiskImpactMitigation
Document uploads exceed Vercel and Server Action body limitshighEach file goes from the browser straight to the backend upload endpoint, never through Next.js. The 10 MB-per-file limit is checked in the browser and on the backend (Spring allows 50 MB).
Shared files (auth.js, /api/sso, proxy.js) break student SSOhighAdditive branches only, behind flow=teacher; a student regression pass in P2 and P7.
Existing stage endpoints (student and teacher) trust userId without a hash checkhighThe new endpoints validate userLoginHash. The existing ones stay as they are because enforcing it would break the legacy JSP; this is tracked as a separate task.
Teacher documents (passport, police verification, salary slip) are public-read in S3highKept for parity, because the admin dashboard opens the links directly. Moving to private objects with signed URLs is a separate task.
AWS access keys are hard-coded in is-rest-api yml and SQL fileshighOutside this plan. Rotating the keys and moving them to env vars or the DB is a separate task.
The contract HTML from the backend is rendered as HTMLmediumSanitize it with DOMPurify, and only allow the signature image and the logo source.
The demo poll runs while the tab is in the background or the teacher leavesmediumBounded refetchInterval, paused when the tab is hidden, and resumed on return.
The 5-minute SSO token expires before the teacher opens the emailmediumThe continue endpoint creates a fresh token on every click within 72 hours.
firstReset values overlap with other rolesmediumAlways check the role together with firstReset.
New timezone code skips the project fallbacklowAsia/Singapore fallback; never overwrite a valid configured timezone.
No automated test framework in is-smslowEvery phase is tested end to end in the browser against the local backend before review, then a full manual QA matrix runs in P7. No new test framework for now.
