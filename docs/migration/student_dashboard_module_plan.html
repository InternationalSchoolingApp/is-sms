02 Approach & Coexistence Toggle

Reuse the already-proven is-sms scaffold. Add a Dashboard Foundation (built once, reused by every future role), then migrate home (calendar first) and each module, each consuming existing Java endpoints via the services/*Api.js BFF. A new backend CONFIGURATION / STUDENT_DASHBOARD_VIA_NEXTJS toggle routes students to Next.js vs legacy JSP per school — exactly like the working ENROLLMENT_VIA_NEXTJS switch — giving per-school rollout and instant rollback.

Reuse as-is (do NOT rebuild): auth.js, proxy.js, utils/backendOrigin.js, utils/payloadEncoding.js, utils/authentication.js, components/providers/QueryProvider.jsx, components/ui/**, components/common/**, globals.css theme, useIntlTelInput, TanStack Query conventions, payment pages.

03 Phase A — Dashboard Foundation prerequisite

Built once; reused by all future dashboard roles (Teacher, Counselor, etc.).

  1. Role shell — route group app/[school]/(dashboard)/ → layout.jsx → DashboardShell (TopHeader + Sidebar + content), mirrors Dashboard.jsp includes.
  2. Dynamic sidebar from USER_RIGHTS — a BFF wrapper over ModulesUtil.getRoleAssignModuleList(school, roleId, "M", 0, userId) → renders the menu; <PermissionGate> for add/update/view/delete. Recommended: faithful DB-driven menu (alt: static student menu — faster but diverges from Java).
  3. useDashboardContext — clone of useEnrollmentContext: session + school settings + logo + theme.
  4. Dashboard-role SSO — extend auth.js/app/api/sso to carry role/roleId/parentUserRole; route student → /{school}/student.
  5. Toggle — backend STUDENT_DASHBOARD_VIA_NEXTJS + a getFinalUrl-style redirect branch on the student dashboard entry.

06 Backend Changes

  • None required to "copy" — reuse existing endpoints via the BFF. Add the STUDENT_DASHBOARD_VIA_NEXTJS toggle + redirect branch.
  • HTML-fragment / Gson endpoints: Recommended — reuse JSON/Gson endpoints directly; for pure HTML-fragment modules add a thin JSON endpoint per module as reached (small addition, not a rewrite). (Alt: parse HTML — rejected as brittle.)
  • Security (parallel): session-derived identity (no body-trusted userId); never send DATABASE_NAME/SESSION_ID to the client.
