01 Executive Summary

International Schooling runs a large multi-school SMS on Spring Boot 3.5.6 / Java 25 (WAR) with a JSP + jQuery + Bootstrap 4 frontend. A separate Next.js 16 app (is-sms) already exists and has migrated one module end-to-end — the student enrollment/signup wizard — using a proven, repeatable scaffold. This plan audits both repositories and lays out how to migrate the remaining role dashboards module-by-module, backend stable, with per-module coexistence and instant rollback.

Five findings that shape the whole plan

#FindingStatusImpact on migration
1Backend auth is a custom server-side Redis HttpSession cookie — no Spring Security, no JWT. sessionUtil.getUser() called 586×.VerifiedNextAuth cannot replace it — it wraps it. Requires same-origin reverse proxy so the cookie is shared.
2Authorization is predominantly frontend-enforced (JSP <c:if>, JS, DB USER_RIGHTS menu/button gating); some backend role guards are dead code.VerifiedA dynamic menu + permission engine must be built first; backend hardening is a parallel prerequisite.
3~Half the endpoints return server-rendered HTML fragments (352 AJAX_PAGE*) or Gson-string JSON for DataTables, not clean DTO JSON.VerifiedPer-module JSON contracts needed before each dashboard UI migrates.
4Feature flags live in a global SETTINGS table with no SCHOOL_ID; ~30 hardcoded schoolId==1/3/5 branches.VerifiedMulti-school config cannot vary per tenant today — a key architectural gap to resolve.
5Extensive committed secrets + weak crypto (MD5 passwords, reversible password store, hardcoded AES key/IV).VerifiedSecurity remediation + secret rotation is a P0 blocker, independent of UI migration.
Recommended approach Strangler-fig: keep the Java backend and JSP app running; migrate one role module at a time into is-sms, each guarded by a backend <MODULE>_VIA_NEXTJS CONFIGURATION toggle (the proven ENROLLMENT_VIA_NEXTJS pattern) so it can be enabled per school and rolled back instantly. Both apps are served same-origin behind one reverse proxy and share the Redis session cookie.

Recommended first implementation phase after approval: Phase 0/1 — secret rotation + Dashboard Foundation (role-aware shell, dynamic menu from USER_RIGHTS, PermissionGate, dashboard-role auth/SSO). Everything else depends on it.

02 Scope & Methodology

Both repositories were reviewed read-only. No Java, JSP, JS, TS/JSX, config, env, DB, or application source file was modified. The only write performed is this HTML document. No dependencies installed, no branches changed, no production/mutation/payment APIs called, no secret values reproduced.

Method

  • Direct reads of core files in both repos (auth, session, datasource, routing, globals, BFF, payload encoding, wizard, config, git metadata).
  • Parallel targeted exploration across: authentication/security, roles/authorization, JSP/routing, JavaScript/libraries, REST API inventory, CSS/theme + multi-tenancy, payments/uploads/external services, per-role flow mapping, the is-sms scaffold recipe, and multi-school architecture.
  • Evidence-based: statements cite file paths / classes / methods. Anything not confirmed in source is tagged Unverified or Open Question.

Coverage & limitations

  • Covered: architecture, auth/session/tenancy, roles & authorization, API surface (grouped), JSP/JS inventory, payments, uploads, external integrations, security, the full is-sms implementation, multi-school config model.
  • Not exhaustively covered (sampled/grouped): every one of 126 controllers method-by-method; every one of ~1,898 endpoints' request/response schema; exhaustive per-DAO SQL tenant-filter review. These are explicitly flagged where relevant and listed as follow-ups in §26.
  • Legacy flags marked Open Question: three dead/commented dashboard routes (/dashboard/school, /dashboard/auditor, /dashboard/hod), SCHOOL_ID 2 & La Senda numeric id, host→slug routing layer.

16 External Integrations Verified

Migration implication: No integration needs a Next.js rewrite — they stay on Java. Next.js only renders UI and links out (chat) or opens redirects (payments). Credentials for all of these live server-side (many in the global SETTINGS table or SCHOOL_SETTINGS_AWS/_MAILS/_LMS).

17 Database & Data-Access Architecture Verified

  • Single shared MariaDB; multi-tenancy by SCHOOL_ID columns. Read/write replica split via RoutingDataSource (by transaction read-only state).
  • Per-school config in SCHOOL_SETTINGS_* tables (clean). Global config/flags/secrets in SETTINGS (no SCHOOL_ID).
  • Program availability via GRADE_LEARNING_PROGRAM_MAPPING (per school/program/grade).
  • JPA/Hibernate repositories + some raw native SQL DAOs (attendance, roster) — these must each carry a SCHOOL_ID predicate.
Data-isolation risks High
  • Global SETTINGS (no tenant) → flags/secrets shared across all schools.
  • Silent fallback: unknown/empty slug resolves to international-schooling/schoolId=1 (SchoolSettingsOfficeServiceImpl:62-66).
  • Cross-school aggregate reads when schoolId==1 (:109) — IS acts as super-tenant; verify every caller is authz-gated.
  • Raw concatenated SQL in some DAOs — dedicated query-level isolation review needed (not exhaustively audited).

30 Final Recommendations & Next Steps

  1. Treat P0 security as a true blocker. Rotate all committed secrets and confirm the production reverse-proxy owner before any new module ships.
  2. Build the Dashboard Foundation once. The dynamic menu + PermissionGate + dashboard-role SSO is the single most important shared piece; everything downstream reuses it.
  3. Make the backend authoritative for authorization in parallel — do not ship dashboard UIs on top of frontend-only enforcement.
  4. Generalize the proven toggle. Every module ships behind <MODULE>_VIA_NEXTJS for per-school rollout and instant rollback.
  5. Order: Student → Parent → Auditor → Teacher → Counselor/Leads → Partner + Role-rights admin → School (largest, last) → Reports/retire JSP.
  6. Close the multi-tenant gaps: per-school config, remove ~30 hardcoded schoolId==N branches, strict slug resolution, confirm host→slug routing.
  7. Resolve the open questions (§26) — especially the three dead routes and the host→slug layer — before scoping School/Auditor/HOD.
