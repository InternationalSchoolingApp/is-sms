4. Frontend (is-sms) — kya badlega

  • services/dashboardApi.js → getSchoolCalendar(): sirf URL dashboard/school-calendar → dashboard/student/school-calendar, jab session STUDENT ka ho. Body wahi ({ userId, startDate, endDate }; naya endpoint userId ignore karega). Response wahi, isliye useStudentCalendar, bootstrap (Tier 1), ClassFeedbackHost, dummy mode — kuch nahi badlega.
  • Koi aur role (agar kabhi) purana URL hi use karega.

5. Security

  • Purana endpoint payload ke userId pe chalta hai (kisi ka bhi calendar mang sakte ho) — usse nahi chhedna.
  • Naya endpoint sirf session user ka calendar dega, aur sirf STUDENT role ko. Isse student ki taraf ka ye IDOR khatam.

6. Kaam ka kram

  1. is-rest-api: StudentSchoolCalendarUtil (student branch copy + RequestCache), controller method, feedback DAO query + service, attendance overload.
  2. Backend compile (mvnw compile).
  3. Diff test: Liliana ke liye purana aur naya dono endpoint — 3 din, 1 hafta, 1 mahina — JSON compare (event order sort karke). Diff khaali hona chahiye. Batch student / orientation / holiday wale din agar test account mile to wo bhi.
  4. Time naapna: dono endpoint same range ke liye.
  5. is-sms: getSchoolCalendar ka URL switch → lint + build → dashboard home aur My Classes browser mein check.
  6. Teacher dashboard (Java) ek baar khol ke dekhna — confirm ki wahan kuch nahi badla (purana endpoint).

Backend restart chahiye hoga (naya controller method). Koi commit nahi — sab uncommitted chhodunga.
