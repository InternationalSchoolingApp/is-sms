26 Nov 2026 · backend POST {school}/dashboard/school-calendar → DashboardSchoolCalendarUtil.getSchoolCalendar() (is-rest-api) · sirf analysis, koi code change nahi.

Faisla: haan, impact hai — ye ek hi Java method student aur teacher dono ke liye chalta hai (aur legacy student, parent, bulk-feedback popup ke liye bhi). Isliye Point 7 ko teen hisson mein baanta:
  • 7a — safe ek request ke andar memo/cache (feedback form mapping, teacher lookup). Output byte-for-byte same rehta hai, sirf queries kam. Teacher dashboard pe bhi koi functional badlaav nahi — wo bhi tez hoga.
  • 7b — test chahiye attendance / feedback ki batch (bulk) queries. Nayi DAO queries lagengi (naya endpoint nahi). Student aur teacher dono ka regression test zaroori.
  • 7c — abhi nahi holidays ki ek-range query. Maujooda holiday query ye nahi batati ki holiday kis din ka hai, isliye bina nayi query ke merge nahi ho sakti — aur home pe sirf 3 din = 3 queries, fayda chhota.

2. Method ke andar kaun sa hissa kis role ke liye chalta hai

Shared — shuru

Session user, payload user, school UUID, dates ki list.

Sirf STUDENT

studentStandard, batch id, apni single classes (getAllClassDetailsForStudent).
Har din: holiday query + batch classes; har batch class: attendance count ×1–2, attendance status, feedback submission, feedback form mapping ×1–2, teacher lookup.

Sirf TEACHER

teacher, standards, providers, apni single classes (getAllClassDetailsForTeacher).
Har din: holiday query + batch classes; har batch class: attendance count ×1–2, feedback submission, feedback form mapping ×1–2.

Shared — single classes loop

Dono role. Har class: attendance count, attendance status, feedback submission, feedback form mapping ×1–2, teacher lookup (+ orientation id agar orientation class).

Shared — activities loop

Dono role. Ek query se activities, phir har activity: attendance count, attendance status, feedback submission, form mapping ×1–2, teacher lookup.

Sirf STUDENT — aakhir mein

Buzz assignments (ek query), active course list (2 queries).

Matlab: ek calendar event pe lagbhag 5–8 DB queries. 3 din mein 6 events = ~40 queries; Week (9 din) ya mahine mein ye kai guna. Ye N+1 hi 7.5s ka mukhya kaaran hai (upar se dev ka read pool 3).

4. Teacher dashboard pe asar — saar

  • Functional asar: 7a se koi nahi — response wahi rahega. 7b se tabhi nahi jab bulk queries exact purani shart rakhein; isliye 7b ke baad teacher ka calendar test karna zaroori.
  • Performance asar: positive — teacher ka calendar bhi tez hoga, khaas kar Week/Month aur bulk-feedback popup (7 din) mein.
  • API contract: URL, request, response format — kuch nahi badlega. Legacy Java pages aur Next dono bina change chalenge.
  • Data: sirf reads hain — koi write/update nahi badlega.

5. Test plan (implement karne ke baad)

  • Badlaav se pehle aur baad ka JSON response save karke diff — student (Liliana) aur ek teacher, 3 range: 3 din, 1 hafta, 1 mahina. Diff khaali hona chahiye.
  • Batch student (agar koi test account ho) — batch classes wala hissa sirf usi se chalta hai.
  • Holiday wala din aur orientation class wala din (orientation id ka hissa).
  • Teacher dashboard (Java) pe calendar khol ke dekhna; legacy student dashboard pe bhi.
  • Time: pehle/baad ka backend time (wahi audit logger) — home 3 din aur My Classes mahina.
